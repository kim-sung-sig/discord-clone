3. SOLID 적용 기준

원칙적용
SRP발행·조회·전달 재시도·권한·빈 조립은 별도 변경 이유다. 같은 트랜잭션으로 지켜야 할 저장 책임은 유지한다.
OCP실제 JDBC/메모리, Kafka/로컬 교체 경계 유지. 예상만 있는 확장 포인트 추가 금지.
LSP어댑터의 권한 거절, 정렬/cursor, 멱등성·재시도 계약을 검증한다.
ISP호출자에게 필요한 좁은 계약은 유지. 수를 줄이려 모든 포트를 합치지 않는다.
DIPdomain → boot/Spring/JDBC 의존 금지. 컨트롤러가 framework-light 구체 유스케이스를 호출하는 것은 허용한다.

PasswordHasher·privacy guard·ExpressionService는 구현 하나라는 이유로 삭제하지 않는다. MessagePublishGuard/MessageContentPolicy/ChannelMessageReadGuard는 람다 빈, MessageMutationGuard는 익명 구현, AttachmentScanner는 allowAll() 람다 구현이 존재한다.

MessagePublicationRelay는 boot와 독립 message-service가 함께 사용한다. 두 런타임과 worker 테스트를 별도로 조사하기 전 1차 통합에서 제외한다.

4. 단계별 실행·완료 조건

  1. A — 미사용 gateway 계약 삭제: 실행 코드 참조 0, gateway 테스트와 boot 컴파일 성공.
  2. B — 5개 단일 구현 통합: 각 interface 파일을 구체 클래스로 바꾸고 Default 파일 5개 제거. 생성자·빈·기존 테스트 갱신. 요청/응답과 정책 동작 동일.
  3. C — 중복 reader 정리: 현행 query의 권한 거절·삭제 제외·cursor 보존을 확인하고 기존 reader/빈 정리. 구형 저장 API는 이 단계에서 보존.
  4. D — 정책/조립 분리: postgres/projection-enabled/권한/moderation 분기와 오류 결과를 보존하는 구체 boot 어댑터 추출.
  5. E — JDBC 책임 분리: 조회 또는 outbox 운영을 하나씩 추출. PostgreSQL에서 원자적 rollback, lease/retry/DLQ, cursor 검증 없이는 완료 금지.
  6. F — 후속 영역 조사: 인증·guild·프런트엔드는 실제 흐름을 읽고 별도 계획을 확정한다. 이번 문서로 일괄 수정하지 않는다.

각 단계는 독립 검수 가능한 변경으로 진행한다. 실패하면 다음 단계로 넘어가지 않는다. 줄 수 감소는 결과 지표이며 할당량이 아니다. 새로운 BaseService·범용 repository·dependency·전역 이름 정리는 추가하지 않는다.

5. 구현 정합성

사용자의 진행 지시에 따라 A→B→C→D→E를 순서대로 수행했다. 각 단계 뒤 집중 테스트를 통과한 후 다음 단계로 진행했다.

단계구현 결과
A미사용 GatewayCommandService 삭제
B다섯 유스케이스의 interface/Default 쌍을 각각 구체 클래스 하나로 통합
C미사용 ChannelMessageReader 실행 경로와 전용 테스트 삭제
D권한과 moderation 정책을 MessageAuthorizationPolicy, MessageContentModerationPolicy로 이동
Eclaim/retry/DLQ를 JdbcMessagePublicationOutbox로 이동. 원자적 savePublished는 저장소에 유지

현재 구조

MessageController → concrete use cases → narrow domain ports
MessageConfiguration → policy wiring
JdbcMessageStore → message/idempotency/read projection/atomic publish save
JdbcMessagePublicationOutbox → claim/retry/dead-letter operations

Blueprint 계약

Review preset: Implementation Review, 90점 이상 및 P0/P1 0건. Blocking ambiguity: 없음. 실행 호출자, Spring profile wiring, JDBC transaction과 PostgreSQL 테스트 소비자를 확인한 뒤 범위를 고정했다.

Expected Changed Files: backend/modules/gateway/src/{main,test}/java/com/example/discord/gateway/**, backend/modules/message/src/{main,test}/java/com/example/discord/message/**, backend/boot/src/{main,test}/java/com/example/discord/message/**, docs/04-report/2026-09-21-code-simplification-plan.report.html.

Competing branches: 단일 구현 interface를 유지하는 선택은 탐색 비용을 남겨 제외했고, 모든 유스케이스를 하나의 MessageService로 합치는 선택은 SRP를 훼손해 제외했다. 선택안은 유스케이스별 구체 클래스 유지와 outbox 운영 adapter만 분리하는 구조다.

System: HTTP adapter → concrete use case → narrow domain port → boot adapter
Class: MessageConfiguration → MessageAuthorizationPolicy / MessageContentModerationPolicy
Behavior: savePublished → message + idempotency + projection + outbox insert → commit
Failure: any SQL/runtime failure → rollback whole transaction

HTTP·event·DB schema 계약은 변경하지 않았다. 사용 중인 JDBC/메모리, Kafka/로컬 교체 경계도 유지했다.
