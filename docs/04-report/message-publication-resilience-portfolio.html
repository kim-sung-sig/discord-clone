  • 테스트에서 Spring Kafka listener container를 멈추고 다시 시작했습니다. 실제 프로세스 강제 종료·재기동은 별도로 재현하지 않았으며, gateway 효과 후 Inbox 기록 전 crash window는 단위 테스트에서 재시도와 안정 eventId 중복 제거로 검증했습니다.
  • 공용 Kafka error handler가 같은 message topic의 gateway/notification consumer group에서 각각 처리합니다. 단일 DB 실패에서 gateway consumer 실패 3회, 전체 retry callback 6회와 DLQ 기록 2건이 관측됐습니다.

VII. 장애 재현 및 실측

첫 lag 계측은 Kafka client의 records-lag-max였습니다. listener를 pause한 테스트에서도 값이 증가하지 않아 RED가 났습니다. 이는 fetch 상태만으로 미커밋 backlog를 설명할 수 없다는 증거였고, consumer group committed offset과 broker latest offset의 차이로 바꿨습니다. 미커밋 파티션은 committed offset 0으로 계산합니다.

서브에이전트 3개가 Outbox, 소비자·DLQ, 실제 인프라 경계를 조사했습니다. 기존 통합 테스트 4개와 단위 테스트가 다루지 못한 장애 순서를 정리하고, 28개 실행 케이스를 추가했습니다. 이 중 9개는 poison 입력의 파라미터 검증입니다.

처음 빠뜨린 원인: 기존 malformed 사례는 문법상 유효한 JSON의 필드 누락만 다뤘습니다. 잘린 JSON 3종을 먼저 실행하자 DLQ 생성도 실패했습니다. JSON 파싱 실패 시 eventId 없이 안전한 메타데이터를 만들도록 수정했고, 같은 파티션의 다음 정상 이벤트가 진행하는 것을 실제 Kafka에서 확인했습니다.

Outbox의 완료 기록과 실패 기록이 연속으로 실패하면 최초 예외가 가려지는 결함도 RED로 재현했습니다. 후속 실패를 suppressed로 보존한 뒤 같은 테스트를 통과시켰습니다. 이미 동작하던 재해 시나리오는 기존 동작 검증으로 기록했으며 새 RED라고 주장하지 않습니다.

실제 프로세스 복구: 자식 JVM이 Gateway SQL 기록을 마치고 Inbox 완료 전에 latch에서 정지한 것을 확인한 뒤 강제 종료했습니다. 동일 Kafka·DB로 새 JVM을 띄워 재발행 없이 복구했고, Gateway 행은 1개, Inbox는 0개에서 1개가 됐습니다. 해당 테스트는 22.185초였습니다.

이번 DB 중단 실행은 실패 3회, 두 group의 retry callback 6회와 DLQ 2건, 장애→DLQ 13,889ms, 재전달→Inbox 198ms, lag 5→0을 기록했습니다. 앞선 실행 수치와 별도인 로컬 단일 실행 결과입니다.

검증 한계: producer 장애는 테스트 전용 무응답 endpoint를 통한 metadata timeout이며 공유 broker 프로세스를 중지한 실험은 아닙니다. DLQ 발행 실패는 handler 반환값을 검증하며 실제 committed offset 장애 증거는 아닙니다. 동시 consumer는 같은 Gateway service를 사용하며 WebSocket 전달 횟수 1회를 증명하지 않습니다. API는 MockMvc 통합 테스트입니다.
