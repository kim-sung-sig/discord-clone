2. 발견 사항

P2 · lag 스케줄러가 일반 예약 작업도 실행

backend/boot/src/main/java/com/example/discord/message/MessageKafkaConfiguration.java:30–35. 유일한 TaskScheduler bean이라 qualifier 없는 @Scheduled에도 기본 scheduler로 선택됩니다. Boot 기본 scheduler 자동설정도 backoff합니다. lag AdminClient 조회와 Outbox relay가 같은 단일 스레드를 공유해 broker/Admin 지연이 relay를 막습니다.

실제 증거: .gradle/message-failure-expansion/pipeline-expanded.xml:832,835,836에 relay/claim thread가 message-publication-lag-1로 기록돼 있습니다. 실제 Spring 7.0.9 router를 사용한 임시 Java 재현도 동일 인스턴스 선택 assertion을 통과했습니다. 현재 테스트는 annotation 값만 확인합니다.

최소 수정: 일반 작업용 기본 taskScheduler를 별도로 등록하고 lag가 차단돼도 relay가 진행되는 context 검증을 추가하십시오. 기존 blueprint/acceptance의 격리 완료 주장도 정정해야 합니다.

P2 · test,postgres에서 GuildService 중복

backend/boot/src/main/java/com/example/discord/guild/GuildConfiguration.java:18. test fake와 postgres 서비스가 함께 등록돼 GuildService를 요구하는 caller의 주입이 모호해집니다. 해당 조합은 startup에 실패할 수 있습니다. 저장소에서 혼합 프로필 실사용은 찾지 못했습니다.

최소 수정: fake 조건을 @Profile("test & !postgres")로 제한하고 혼합 프로필에서 JDBC 서비스 하나가 선택되는 테스트를 추가하십시오. Moderation fake는 이미 이 조건입니다. 이번 검수에서 혼합 프로필 startup 테스트는 새로 실행하지 않았습니다.

P2 · 수신자별 전체 Guild 재조회

backend/boot/src/main/java/com/example/discord/event/ServerEventRecipientResolver.java:23, backend/boot/src/main/java/com/example/discord/notification/MessageMentionRecipientResolver.java:39. 수신자별 canViewChannel이 JDBC Guild 전체를 다시 읽습니다. 멤버 M명·채널 C개에서 대략 M×(C+5)의 조회가 발생할 수 있습니다. 영속화로 기존 메모리 호출의 비용이 커진 경로입니다.

권고: 큰 guild의 이벤트/@everyone fanout에서 query count와 지연을 측정하고 필요하면 한 snapshot에서 권한을 일괄 계산하십시오. 운영 처리량은 측정하지 않아 비차단 P2입니다.
